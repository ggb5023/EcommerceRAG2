## 2. 目标：两个界面，两套标准

把现在的"能点的表单集合"改成两个界面：

- **商家管理台**：桌面优先，一屏答一个商家问题；
- **顾客端**：手机优先，顾客在手机浏览器里能顺畅问答、查看引用。

| | 商家管理台 | 顾客端 |
| --- | --- | --- |
| 使用者 | 店主/客服，坐在电脑前 | 顾客，几乎全在手机 |
| 设备 | **桌面 only**（≥1280 宽） | **手机优先**（360–430 宽） |
| 适配策略 | 不做响应式，固定最小宽度 | 必须响应式，触控优先 |
| 表格/多列 | 允许，超宽横向滚动 | 禁止，一律卡片 |
| 交互 | 鼠标、右键、多选、批量 | 单手、点按、底部弹出 |
| 验收设备 | 1280×800、1920×1080 | iPhone 14 / Pixel 5 / iPhone SE |

**商家端窄屏处理**：视口 < 1024 时顶部显示"管理台请使用桌面浏览器"提示条，
但**不阻断**（允许横向滚动，不隐藏任何功能）。

### 现有问题（改什么）

| 问题 | 表现 |
| --- | --- |
| 无设计系统 | 每页自定间距/字号/按钮，视觉不统一 |
| 信息架构按接口分组 | 页面按 sources/versions/reviews 分，而不是按商家任务分 |
| 关键状态不可见 | 导入后不知切成什么样；审核时看不到为何 needs_revision；命令无进度与失败原因 |

**判断标准**：每一屏要能回答用户心里的一个问题。答不出来不是组件问题，是信息架构问题。

## 3. 硬约束（违反即停）

1. **不改后端接口**：纯前端改造。确需后端配合（字段缺失等）先写进 ADR，不擅自改契约。
2. **UI-only 矩阵按实测口径维护**：`go/internal/admin` 共 **34 条**唯一路由，其中 **33 条已有 UI**。
   矩阵原先只登记 31 条，**漏登记 2 条**：`POST /admin/v1/merchant/versions/batch-approve`、
   `POST /admin/v1/merchant/versions/{id}/suggestion`——这两条前端早已在用（`AdminApp.vue:207`、`:178/189`），
   属登记遗漏，不是功能缺失。
   真正无 UI 的只有 **1 条**：`GET /admin/v1/merchant/usage`（随 0021 的 token 用量界面实现）。
   硬指标：**已实现的 A 级入口不得减少**；阶段 3 只需补 `usage` 一条实现，另把 2 条登记进矩阵。
3. **浏览器测试必须同步**：现有 34 条断言依赖中文文案；改文案 = 同提交改测试，
   且**改测试适配新文案**（文案服务商家，不为测试凑合）。
4. **关键元素补 `data-testid`**：先补，再改文案；让后续改文案不再牵动测试。
5. **不引入 UI 框架的路由/权限/状态管理**：只取布局与视觉；鉴权仍由服务端与现有 session 决定。
6. 一页一次提交；每页迁移后 `check.sh` + 前端测试 + 该页浏览器测试全绿。
7. **两端不合并到同一个提交**：管理台与顾客端验收标准不同，必须分开。

## 6. 设计语言（tokens）

`frontend/src/styles/tokens.css`，亮/暗两套：

```
--color-bg / --color-surface / --color-border
--color-text / --color-text-muted
--color-primary / --color-success / --color-warning / --color-danger
--space-1..8（4px 基准）
--text-xs..3xl
--radius-sm/md/lg
--shadow-sm/md
```

**状态色语义全站固定**（不得各页自定）：

| 语义 | 颜色 | 用在哪 |
| --- | --- | --- |
| 成功 / 已发布 | success | 版本状态、命令完成、测试连接通过 |
| 警告 / 需关注 | warning | needs_revision、过期内容、unclassified |
| 危险 / 阻断 | danger | 发布失败、越权、密钥无效 |
| 中性 / 待处理 | muted | pending、草稿 |

**硬规则**：agent 的结论一律用中性色 + "AI 建议"标签，**不得用成功色**——
避免让人误以为"AI 说可以 = 已经批准"。

## 7. 顾客端移动适配规范

### 7.1 视口与基础

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

- 高度用 **`100dvh`**（不用 `100vh`，否则 iOS 地址栏收缩时输入框被遮）
- 安全区：底部输入条 `padding-bottom: env(safe-area-inset-bottom)`
- 输入框字号 **≥16px**（低于 16px 时 iOS 会自动放大页面）
- 触控目标 **≥44×44px**，间距 ≥8px

### 7.2 布局

| 区域 | 移动端形态 |
| --- | --- |
| 会话区 | 占满屏幕，消息气泡最大宽度 85% |
| 输入条 | 固定底部，随键盘顶起（监听 `visualViewport` 的 resize） |
| 引用 / 证据 | 点角标 → **底部抽屉**（不是右侧栏） |
| 顶部 | 店铺名 + 一条极简状态（"资料更新于 …"），可折叠 |
| 历史会话 | 抽屉，从左侧滑出 |

### 7.3 交互细节

- 流式渲染时保持滚动贴底；用户上滑后**暂停自动滚动**，出现"回到最新"按钮
- 长按消息 → 复制；引用角标点击区域 ≥32px
- 发送中禁用发送键并显示状态；失败可重试，不丢草稿
- 断网/超时提示显示为消息流内的一条系统消息，不用弹窗
- 首屏 JS 体积目标 **≤ 100KB（gzip）**（基线见第 11 节；200KB 太宽，等于没有约束）

### 7.4 验收

用 Playwright 设备描述符跑顾客端用例：`iPhone 14 (390×844, DPR3)`、`Pixel 5 (393×851)`、
`iPhone SE (375×667)`。

至少断言：输入条不被遮挡、引用抽屉能开能关、长回答可滚动、横竖屏切换不破版。

## 8. 页面级改造清单

### 8.1 导入向导（商家端，桌面）

- **商家问**：我传的这批文档有没有问题？切成了什么样？
- 三步横向进度（上传 → 预检 → 确认），每步一屏，不堆在同页。
- 上传：拖拽区 + 文件清单（名称/大小/状态），支持整批删除。
- 预检：按 `issue_code` 分组的卡片（block 红 / warn 黄），每条可展开看 `snippet` 高亮。
- 确认：底部固定操作条"20 份将被导入，其中 4 项需注意" + 二次确认。
- 撤回：整包撤回 + 二次确认 + 置灰显示撤回时间。
- 参考：Dify 上传与分段预览；RAGFlow chunk 高亮。

### 8.2 审核列表（商家端，桌面）

- **商家问**：这些待审的东西，AI 怎么看？我要批哪些？
- 表格 + 左侧筛选（全部 / 需修改 / 有建议 / 无建议）+ 顶部批量操作条。
- "AI 建议"列：中性标签（可审核 / 需修改 / 无建议）+ 前两条理由。
- 展开行：完整理由 + 证据片段（引用原文），高亮命中。
- 多选 → 批量确认：弹窗必填理由，显示"共 N 条，其中 M 条需修改"。
- 逐条结果：成功 / 过期 / 失败三类计数 + 失败可展开 code/detail；过期项给"重新生成建议"。
- **发布仍是单条**，按钮在详情页，不与批量确认放在一起。
- 参考：vben 表格工具栏；RAGFlow 证据展示。

### 8.3 客户试问 / 客服工作台（商家端，桌面）

- **商家问**：这个问题它答得对吗？依据在哪？
- 左对话、右证据栏（可收起）；流式渲染 + "检索中 / 生成中"状态。
- 引用角标 `[1][2]` → 点击右侧定位到对应片段。
- 复制按钮：不可用时显示原因（无引用 / 需追问，对应 0005 规则）。
- 每条回答下方显示：命中文档数、是否含快照数据、时效声明是否出现。
- 参考：Vercel AI Chatbot 引用角标；Open WebUI 消息操作。

### 8.4 顾客端问答页（**移动优先，独立分支**）

- **顾客问**：我的问题有答案吗？凭什么这么说？
- 单列全屏布局，严格遵守第 7 节规范。
- 回答下方引用以"来源 1 / 来源 2"折叠列表呈现，点开底部抽屉看原文片段。
- 时效声明必须可见（快照数据不得隐藏）。
- 参考：Open WebUI 移动布局；Vercel AI Chatbot 引用卡片。

### 8.5 供应商配置（P3，商家端桌面，阶段 2）

- 卡片列表（名称 / kind / base_url / last4 / 状态点 / 启用开关）+ 五步抽屉。
- 测试连接：按钮 → 状态点变化 → 失败显示分类（DNS / 连接拒绝 / TLS / 401 /
  模型不存在 / 维度不符 / 限流）。
- 无 key 的本地端点允许保存并标记 `no_egress`。
- 明示："更换供应商会改变回答质量，历史用量按当时记录保留"。
- 参考：LibreChat 表单顺序；Open WebUI 连接表。

### 8.6 店铺设置 / 权限与审计（商家端，桌面）

- 设置：分组卡片（基本信息 / 模型辅助开关 / 通知），开关旁写清影响面。
- 权限：申请列表 + 审批人视角；审计：可按 actor/action/时间筛选，导出 CSV。

## 9. 阶段与验收

### 9.0 与后端重构的顺序规则（必读，冲突时以此为准）

后端重构见 `docs/backend-refactor-plan.md`（P-A turn 引擎 / P-B admin store / P-C Python 巨型函数），
其中第 1.6 条写明"**重构期间功能冻结：除阻塞性 bug 外不接新功能**"。本方案必须服从该冻结。

| 本方案阶段 | 能否与后端重构并行 | 理由 |
| --- | --- | --- |
| 阶段 1（设计系统） | ✅ 可以 | 只改 `frontend/`，不触及 Go/Python，不新增接口 |
| 阶段 2（P3 供应商页） | ❌ 不行 | 属新功能，且依赖 P3-3 后端接口；必须等 P-A/P-B/P-C 完成、冻结解除 |
| 阶段 3（页面迁移） | ❌ 不行 | 迁移会改 admin 视图，与 P-B 的 admin store 拆分同区域，合并冲突代价高 |
| 阶段 4（顾客端移动版） | ⚠️ 谨慎 | 不新增后端接口，但会改路由与静态资源；建议 P-C 之后 |
| 阶段 5（全量走查） | ❌ 不行 | 必须在所有重构与迁移结束后 |

**并行铁律**（若确实要并行）：

1. 两个工作流必须从 `main` 各拉独立分支，**不得共用工作区**；
2. 前端分支只允许改 `frontend/**` 与 `docs/**`，越界即停；
3. 任一分支合并前先 rebase 到最新 `main` 并重跑 `check.sh`；
4. 先合并的一方负责更新 `docs/ui-only-acceptance.md` 的对应行。

**推荐顺序**：m8 合并 → 阶段 1（设计系统）→ 后端 P-A/P-B/P-C → 阶段 2–4 → 阶段 5。

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| 1 | tokens + 6 个基础组件（Button/Input/Dialog/Table/Tabs/Toast）+ SidebarLayout + 关键元素补 `data-testid`；现有页面套骨架，**业务逻辑零改动** | check.sh 全绿、前端测试 ≥37、现有浏览器测试全过（文案未改不该红）、截图 3 张存 `.local/redesign/` |
| 2 | P3 供应商配置页（新系统）+ 店铺设置页迁移 | 新增 `provider-setup.browser.mjs` 通过 |

> 阶段 4 可与阶段 2–3 并行，但**不得合并到同一个提交**。

**关于现有浏览器断言的一个兜底**：换组件后若某条断言失败，先判断原因再改：

1. 若是**文案变了** → 同提交改断言，让断言适配新文案；
2. 若是**DOM 结构变了**（如按钮文本被塞进 slot、`getByText` 匹配不到）→ 优先调整组件输出，
   保持可访问性语义（`role` / `aria-label` / 文本节点）不变；
3. 不得为了让断言通过而在组件里塞无意义的 wrapper 或隐藏重复文本；
4. 若必须改定位方式，改用 `data-testid`，并在同一提交里补齐 `data-testid`。

## 11. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 文案改动导致 34 条断言大面积红 | 先在阶段 1 补 `data-testid`，再逐页改文案；改一页跑一页 |
| shadcn-vue 与现有样式冲突 | 用 `@layer` 隔离；过渡期保留原样式类 |
| 迁移中丢功能（如撤回按钮） | 迁移前对照矩阵逐行勾选，迁移后复验 |
| 设计反复 | 阶段 1 定死 tokens 与 6 个组件，后续只允许组合，不允许新造 |
| 顾客端被当成"顺手做" | 单独分支、单独立项验收；移动用例不过不算完成 |
| iOS 键盘遮挡输入框 | 必须用 `100dvh` + `visualViewport` 监听，不接受"看着没问题" |
| 新增 6 个依赖导致体积暴涨 | **实测基线（2026-10-27）：单包 gzip 69,202 B / raw 199,382 B**。阶段 1 后目标 gzip ≤ 90KB（基线 +30%），超过必须在 0024 说明原因；每阶段结束复测 |
| 一次引入 6 个库被视为"顺手加依赖" | 0024 决策记录里必须逐条写明用途与替代方案，并说明为何不引入 vben 整包模板 |
| 与后端重构功能冻结冲突 | 见第 9 节 9.0：阶段 1 可并行，阶段 2–5 必须等后端 P-A/P-B/P-C 完成 |
