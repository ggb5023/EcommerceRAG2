# 0025 代码级规则：不复制指令、阶段函数只做一类事、阶段函数不碰框架对象

- 状态：已采纳
- 日期：2026-10-28
- 关联：[0004](0004-retained-invariants.md)（11 条不变量）、[0021](0021-usage-log-instead-of-budget.md)

## 背景

重构期间反复出现同一类问题，它们既不是产品缺陷，也不是架构错误，而是**实现层面的坏习惯**：

1. **同一条指令被抄到多份文档**。0021 落地后，预算口径在 7 份文档里各写一份；同一段 SQL 统计口径出现
   71 / 67 / 126 / 127 四个数字。读者无法判断该信哪个，审查时也无法机械验证。
2. **一个"阶段函数"同时干几件事**。`runTurn` 一个函数里同时做状态迁移、SQL、gRPC 调用、SSE 推送；
   改动任何一角都要读完整段，测试也只能整段跑。
3. **阶段函数顺手拿了框架对象**。一旦函数签名里出现 `*Handler`、`*gateway`，写法就会自然变成
   "读会话 → 写响应 → 顺手落库"，阶段边界消失，单测退化。

三条规则针对这三件事，都尽量做成**可机械检查**的形态。

## 决定

### R1 文档不复制指令，只链接到唯一来源

- 同一条指令（`--flag`、`ENV_KEY=`、`bash scripts/...`、`python3 scripts/...`）只在一个文档里定义，
  其它文档写"见 <链接>"。
- 执行方式（**硬门禁**）：`scripts/check/check-docs-drift.py`
  - 同一指令出现在 **≥2 份**非 `docs/decisions/` 文档 → 警告并列出来源；
  - 出现在 **≥3 份且取值/参数不一致** → 失败（这正是 71 vs 67 那类漂移）。
  - 已废弃的配置键（`V2_ONLINE_BUDGET`、`provider-budget`）继续按 0021 的口径检查，发现即失败。
- 允许的重复：`docs/decisions/`（历史记录不改）、讨论这些键的重构文档（白名单见脚本）。
- 例外：某一份文档同时列出该键的全部取值（三态开关、按用例映射的 env）时，视为**权威定义**，不判漂移；
  判定逻辑以本决策为准，脚本只负责执行。

### R2 阶段函数只做一类工作

- "一类"指：SQL / 模型调用 / 序列化 / 纯判断（互斥）。
- 拆分后每个阶段函数 **≤80 行**；触碰两类以上必须再拆。
- 执行方式（**软门禁**）：写进 `docs/backend-refactor-plan.md` P-A 的验收条款，
  汇报时必须给出每个函数的行数与触碰类别统计。为什么不做成脚本：类别判断依赖语义，
  机械统计只能数行数，容易给出"通过"的假信号。

### R3 阶段函数不接触框架对象

- 阶段函数的签名里不得出现 `*Handler`、`*Server`、`*Gateway`（含本仓库的 `*gateway`）；
- 函数体内不得出现 `g.xxx` 形式的字段访问。
- 执行方式（**硬门禁**）：`scripts/check/check-stage-boundaries.py` 扫描
  `go/internal/gateway/turn_*.go`；文件尚未拆出时打印 `SKIP` 并返回 0，W2 步 3 落地后自动生效。
- 需要 HTTP 细节时，由调用方（`turn_*.go` 之外的适配层）把纯参数传进来，阶段函数只返回数据与错误。

## 与 11 条不变量的关系

- [0004](0004-retained-invariants.md) 与 [architecture](../architecture.md#必须保留的设计约束) 的 11 条是**产品承诺**：
  单写者、失败关闭、引用可追溯、冻结评测集等，任何情况下不得为了重构方便而放宽。
- 本决策是**实现约束**：它约束"怎么写"，不改变"系统必须做到什么"。
- 冲突时**不变量优先**。典型例子：为了让阶段函数满足 R3 而把权限判断搬到别的包，会破坏"权限只由 Go 决定"；
  正确做法是让阶段函数接收已判定的 scope（数据），而不是自己判定。
- 因此本决策只新增检查脚本与验收条款，**不修改 `docs/architecture.md` 的任何一条**。

## 备选方案

| 方案 | 链接 | 不采用理由 |
| --- | --- | --- |
| 只靠评审，不写检查 | [Google eng-practices: code review](https://google.github.io/eng-practices/review/) | 本仓库的质量门槛由 agent 评审承担（0015），纯人工约束在长周期里必然衰减；R1/R3 恰好可以机械判定 |
| 把三条规则写进 architecture 的 11 条 | [本仓库 architecture](../architecture.md) | 不变量是产品承诺，混入实现偏好会让"违反即回退"的范围失控；实现约束应可随重构结束而更新 |
| 用 lint 规则（如自定义 golangci-lint） | [golangci-lint](https://golangci-lint.run/) | 需要引入新工具与配置维护；本仓库已有 Python 检查脚本的统一入口（`check.sh`），复用成本更低 |

## 后果

- `check.sh` 快速层新增两项：`docs-drift` 与 `stage-boundaries`。
- R1 的警告不会失败，但会在每次门禁输出里列出重复来源，促使后续收敛；
  失败条件只针对"≥3 份且不一致"，避免把合理的多文档引用判死。
- R2 不产生机械信号，靠 W2 的汇报格式兜住；若后续发现评审执行力度不足，再考虑把它机械化。
