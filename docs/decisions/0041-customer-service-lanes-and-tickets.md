# 0041 售前/售后分轨、工单与只读订单事实

- 状态：已采纳
- 日期：2026-11-07
- 工作包：[81](../workpackages/81-service-lanes-schema.md)、[83](../workpackages/83-customer-service-lanes.md)、[84](../workpackages/84-after-sales-facts.md)
- 关联：[0028](0028-orchestration-boundary.md)、[0005](0005-copyable-reply-policy.md)、[0021](0021-usage-log-instead-of-budget.md)、[0034](0034-product-table-import.md)

## 1. 问题

顾客通道目前只有一条链路：任何问题都走检索问答，未解决时转人工，没有服务类型、
没有订单上下文、也没有工单。用户要求把客服拆成两条轨道：

- **售前**：商品、尺码、政策、配送等咨询，不依附订单；
- **售后**：围绕一个订单的咨询，AI 只读查询订单/物流/库存/价格，未解决转人工工单。

工程还需要真实商品/库存/订单概念。商家的实时数据不能写进知识库（0034/0035 已定：
库存与价格必须来自 facts provider，而不是 `catalog_sku`），因此要有一个可复用的
模拟电商后端与拟真数据集。

## 2. 决定

### 2.1 两条服务轨道

| | 售前 `pre_sales` | 售后 `after_sales` |
| --- | --- | --- |
| 入口 | 顾客默认选择 | 顾客选择并填写订单号 |
| 订单号 | 禁止携带 | 必填，创建会话时绑定到会话 |
| AI 数据 | 只读知识库（现有链路） | 知识库 + 只读订单事实 |
| 转人工 | 保持现有语义，不建工单 | 首次转人工创建工单 |
| 终态 | 仍由 Go 决定 | 仍由 Go 决定；工单状态也是 Go 独占 |

服务类型与订单号在会话创建时确定并写入 `customer_conversation`，之后不可改。
会话创建幂等键复用但服务类型或订单号不同 → `409`。

### 2.2 工单生命周期（Go 独占）

```
OPEN ──claim──▶ ASSIGNED ──resolve──▶ RESOLVED
  ▲                 │                     │
  └─release/requeue/└────close/resume-ai──┴──▶ CLOSED
    lease 过期回收
```

- 工单在售后会话**首次** `queueTx` 转人工时创建；AI 已解决的售后不产生工单。
- 同一会话同时只有一个活动工单（`OPEN`/`ASSIGNED`），部分唯一索引保证。
- `claim`→`ASSIGNED`；`release`/`requeue`/租约回收→`OPEN`；新增 `resolve`→`RESOLVED`
  且会话 `CLOSED`；`close`/`resume-ai`→`CLOSED`。
- 所有迁移与既有会话行锁同事务；Python 与管理端不写 `customer_ticket`。

### 2.3 售后 AI 只读

- 允许的事实工具：`get_order_status`、`get_logistics`、`get_stock`、`get_price`。
- 订单号**只**来自会话绑定值，模型输出的其它订单号一律视为越权 → 澄清，不查询。
- 禁止：退款、改地址、取消订单、写订单/库存/物流。回答只能陈述查询结果与政策。
- 证据与事实都为空 → 转人工；任一存在且回答合格 → 可以回答。
- 终态前 Go 重新调用 facts 做授权与绑定复验；不要求值相同，答案带 `observed_at`。
- 事实快照写入执行记录 `facts_json`，供管理台审查与幂等重放。

### 2.4 订单号即凭证（v1 明确限制）

顾客端是匿名会话，v1 没有购买人验证；**知道订单号就视为有权查看该订单的只读事实**。
风险与缓解：

- 只读，不能退款/改址/取消；
- 订单查询按店铺隔离，未知订单与错店铺一律 404/403，不泄露存在性；
- 管理台审查页不展示顾客身份、会话 ID、IP 或 cookie；
- 后续版本可加手机号后四位或一次性验证码，届时以新决策替换本节。

### 2.5 引用或事实快照

0005 的复制条件第 3 条改为：**至少 1 条有效引用，或至少 1 份非 mock 的事实快照**
（售后事实型回答）。其余条件不变：非 mock、ANSWER、Go 判定、前端只读。
员工建议回复仍要求引用（`factCount=0`），不放宽。

### 2.6 前台只留回答，引用后台审查

员工/商家 AI 辅助前台只展示回答文本与复制/采纳操作；引用、证据、事实快照移到管理台
「回答与引用」页，按店铺范围审查。顾客聊天保留引用抽屉（顾客需要知道依据）。

## 3. 边界与理由

- 终态与工单状态只能在 Go 决定（0028）；Python 只产出回答候选、澄清与 confidence。
- 事实查询走既有 `facts.Provider` 契约（HTTP：`GET /v1/facts/{tool}`，版本/租户/店铺/
  资源绑定、`observed_at`、`is_mock`），不新增旁路。
- 库存/价格不落 `catalog_sku`（0034/0035）：知识库只描述商品，实时值来自 facts。
- 拟真数据集在仓库内可复现生成，无 PII、无外网抓取、不统计货币金额（0021）。

## 4. 备选方案

| 方案 | 不采用理由 |
| --- | --- |
| 售后也允许模型自由解析订单号 | 越权查询；模型幻觉会变成真实泄漏 |
| 把库存/价格写进商品表 | 破坏 0034/0035 的实时事实边界，且没有同步机制 |
| 售前转人工也建工单 | 改变既有 smoke 语义，收益低；先只覆盖售后 |
| 售后 AI 直接执行退款/改址 | 高风险写操作，v1 明确只读 |

## 5. 后果

- 新迁移 `0058`：会话服务类型/订单号、两条执行链路的 `facts_json`、`customer_ticket`。
- `RequestContext` 增加 `service_type`(29) 与 `customer_order_id`(30)，进入签名 scope。
- 顾客入口需要先选服务；售后必须填订单号。
- 新增模拟电商后端（`commerce-sim`，仅 loopback，不参与 selfhost）与仓库内的
  `commerce-lab-v1` 拟真数据集；开发栈可一键起。
- 管理台新增「回答与引用」审查页；员工/商家前台去掉引用展示。
