# 0009 顾客跨设备历史的两条路线（提议）

日期：2026-10-25　状态：提议

## 背景

M4 只做商家与员工的本地账号。顾客侧继续使用匿名 `customer_identity` + `customer_session`（见迁移 0026）：会话绑定浏览器 Cookie，换设备或清 Cookie 后历史不可找回。ROADMAP 把跨设备历史放在 P2，需要先决定路线，再决定是否投入。

本记录只做比较，不改变现状；在用户确认前不实现任何一条。

## 两条路线

**A. 会话凭据码**：顾客在旧设备生成一次性凭据码（短数字/字母串，限时、限次），在新设备输入后把新会话绑到同一 `customer_identity`。不收集邮箱，不需要外发通道。

**B. 邮箱注册**：顾客用邮箱 + 密码（或邮箱验证码）注册账号，历史与会话挂到账号上。

## 四类成本对比

| 成本 | A 会话凭据码 | B 邮箱注册 |
|---|---|---|
| SMTP / 外发依赖 | 无外发通道；凭据码在页面展示、由顾客手工抄写 | 需要 SMTP 服务、发信域名、退信与限流处理；生产环境必须新增运维组件 |
| PII 与合规 | 只处理会话标识，不新增个人数据字段；泄露面小 | 收集邮箱与密码哈希，属于个人信息；需要隐私说明、保留期限、加密与访问审计 |
| 注销与导出 | 注销即撤销会话绑定；导出范围就是会话消息 | 需要账号注销、数据导出、邮箱变更与找回流程；涉及删除与备份留存的一致性 |
| 身份合并 | 合并即把新会话挂到旧 `customer_identity`；冲突规则简单（以最新绑定为准） | 多设备、重复邮箱、历史匿名会话归属都需要合并策略；错误合并会串号 |

## 倾向（待确认）

A 的工程与合规成本明显更低，且不引入 SMTP；代价是顾客换设备时需要旧设备仍可用。B 的体验更接近常见电商，但会把本项目从「知识引擎」推向账号系统，需要额外的合规与运维投入。

## 后果

- 在确认前，M4/M5 不引入 SMTP 依赖、不发注册接口、不改 `customer_identity`/`customer_session` 结构。
- 若选择 A，需要新增一次性凭据码表与会话绑定接口；若选择 B，需要先补隐私说明与发信组件，二者都要新的迁移。
